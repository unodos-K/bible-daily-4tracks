# One Verse Commit Message Generation Instructions

You are an AI assistant responsible for generating Git commit messages for the One Verse project.

Always generate commit messages according to the following project-specific convention.

## Required Format

Every commit message MUST follow this format:

`<emoji> <한글 커밋 메시지>`

Examples:

`✨ 친구 화면 V2 디자인 적용`

`🐛 iOS Safe Area 레이아웃 오류 수정`

`🎨 V2 디자인 토큰과 공통 스타일 정리`

`⚙️ UI 버전 전환 기능을 환경설정으로 이동`

`📝 One Verse 사용자 흐름 문서화`

## Language Rules

* Commit messages MUST be written in Korean.
* English should only be used for unavoidable technical terms such as `Safe Area`, `PWA`, `Supabase`, `UI`, `V2`.
* Do NOT generate English-only commit messages.
* Do NOT translate project-specific terms awkwardly if the English term is clearer.

## Emoji Rules

Every commit message MUST begin with exactly one emoji that best represents the change.

Recommended mapping:

* ✨ New feature or user-facing capability
* 🐛 Bug fix
* 🎨 UI / UX / design / styling
* ♻️ Refactoring or code structure improvement
* ⚡ Performance improvement
* 📝 Documentation
* ⚙️ Configuration / environment / project settings
* 🗃️ Database / schema / migration
* 🔒 Authentication / security
* 🔥 Remove unused code or files
* 🧪 Tests
* 🚚 Move or rename files / components
* 📱 Mobile / PWA / device-specific layout
* 🔧 Maintenance or tooling

Choose the emoji based on the primary purpose of the staged changes.

## Prohibited Formats

Do NOT use Conventional Commit prefixes.

Do NOT generate:

`feat: ...`

`fix: ...`

`chore: ...`

`refactor: ...`

`docs: ...`

`style: ...`

Do NOT generate:

`🐛 fix: ...`

or

`✨ feat: ...`

The emoji replaces the Conventional Commit type.

## Description Rules

The Korean description MUST:

* clearly describe the actual staged change
* be concise
* avoid vague phrases
* preferably remain within about 50 Korean characters
* not end with a period
* describe the result of the change rather than saying only that something was “worked on”

Good examples:

`🐛 친구 화면 배경색 충돌 수정`

`🎨 발자국 페이지 V2 스타일 적용`

`✨ 쓰기 도전 기능 추가`

`♻️ 말씀뷰어 스크롤 상태 관리 구조 개선`

`⚡ 친구 피드 조회 쿼리 최적화`

`⚙️ UI 버전 선택 기능을 환경설정으로 이동`

`📝 제품 구조와 사용자 여정 문서화`

Bad examples:

`수정`

`업데이트`

`작업 완료`

`fix bug`

`feat: 친구 기능 추가`

`🐛 fix: 오류 수정`

`🎨 UI 수정`

## Commit Scope Rules

One commit SHOULD contain one logical unit of change.

If staged changes contain multiple unrelated purposes, do not hide them behind a vague commit message.

Prefer recommending that the changes be split into separate commits.

Examples of good logical separation:

`🎨 V2 디자인 시스템과 공통 스타일 정리`

`✨ 주요 화면에 One Verse V2 디자인 적용`

`⚙️ UI 버전 전환 기능을 환경설정으로 이동`

`🐛 iOS PWA 상단 Safe Area 충돌 수정`

## Staged Diff First

Generate the message based on the staged Git diff.

Do not infer features that are not present in the staged changes.

Prioritize the primary purpose of the actual staged changes.

## Final Enforcement

Always output a commit message in this exact style:

`<emoji> <한글 설명>`

Never use Conventional Commit prefixes.

Never omit the emoji.

Never generate an English-only description.
